RenalGenetics Decision Support · Validation

Running the validation study

How to extract the data, score it against the model, and read what comes back. Written for whoever is doing the extraction and whoever runs the numbers — usually two different people.

Design
Retrospective blinded case series
Sampling
Consecutive patients who had a renal gene panel sent
Primary endpoint
Calibration — observed diagnostic yield vs predicted p(genetic)
Secondary
Differential ranking accuracy; eligibility agreement
Pilot size
100 patients (template capacity)
Not in scope
Variant interpretation module — deferred to a prospective MDT comparison
Why calibration is primary

The model currently assumes about 15% of the pre-test population has a modelled monogenic cause. Enriched nephrology cohorts typically run 20–40%. Observed yield in a consecutively-tested cohort tests that assumption directly, and it moves every posterior in the app. Ranking accuracy at n=100 gives roughly 30 gene-positive cases — a ±15% confidence interval — so treat it as exploratory and pre-specify extension to ~300 if the pilot holds.

01

Extract the data

Everything goes into RenalGenetics_Validation_Template.xlsx — 49 columns across three sheets, with room for 100 patients. Row 1 is a group banner, row 2 holds the column names, and patient data starts at row 3. Row 3 ships with a worked example; overwrite it.

Split the work in two

The blinded block runs from Patient_ID through Ctx_APOL1_consented. Complete it without sight of the genetic result. The result block — Panel_tested, Result, Specific_diagnosis, Variant_zygosity, Model_condition — is filled in a separate pass, ideally by a different person.

The mistake that quietly loses data

The app only shows a feature's controls once the matching box is ticked in the presentation picker. A patient whose Hearing_loss = Y but whose Pres_Haematuria = N has, as far as the app is concerned, no hearing loss at all — that field lives inside the haematuria branch.

The scorer reproduces this behaviour deliberately, because scoring hidden features would flatter the tool being tested. Tick every presentation that applies before filling anything below it. Rows where the gate drops a recorded feature come back flagged in the warnings column rather than failing silently — but it is far better to get it right at extraction.

Recording the genetic result

Three rules matter more than the rest:

  • Variant_zygosity is required whenever a P/LP variant is reported. It cannot be reconstructed later, and it decides the COL4A3/COL4A4 mapping.
  • A heterozygous COL4A3 or COL4A4 variant maps to COL4_het, not Alport_AR. These are separate conditions with priors differing about ninefold. An earlier version of the lookup sent all COL4A3/4 variants to Alport_AR; if you were briefed on that version, this is the change.
  • A P/LP variant in a gene the model does not cover is Not_modelled, never NoGenetic. Those patients are genetically positive, and counting them as negatives would drag observed yield downward — corrupting the primary endpoint.

The full lookup is on the Instructions sheet, and every column is defined on the Data Dictionary sheet.

02

Run the scorer

scripts/run_validation.R runs the eligibility scorer and the Bayesian differential over every row, without going through the app. It exists because hand-entering 100 patients into the Shiny interface is not realistic, and because the model was otherwise only reachable through the app's reactive layer.

What it needs

  • R, with Rscript on your path. Developed against R 4.6.0.
  • The openxlsx package — the only dependency beyond base R, used to read the spreadsheet. Install with install.packages("openxlsx").
  • A checkout of the repository, and your working directory must be the repository root. The script sources data/ and R/ by relative path and stops with a clear message if it cannot find them.
  • The completed template.

What to type

cd /path/to/RenalGenetics-Decision-Support
Rscript scripts/run_validation.R

# or, naming the input and an output prefix explicitly:
Rscript scripts/run_validation.R my_extraction.xlsx pilot1

With no arguments it reads RenalGenetics_Validation_Template.xlsx and writes files prefixed validation. The first argument is the input workbook; the second is the output prefix.

What it does, in order

  1. Loads the model parameters, panel definitions and scoring code.
  2. Runs a fidelity check — see below — and prints the result.
  3. Reads the Data Entry sheet, skipping rows with a blank Patient_ID.
  4. For each patient: rebuilds the app's inputs, derives the HPO term set, scores all 12 panels for eligibility, and runs the Bayesian update.
  5. Writes <prefix>_results.csv and <prefix>_summary.txt.
The fidelity check

Model parameters are looked up by exact string. If the app's wording and a parameter key ever drift apart, the modifier silently stops applying — no error, just a quietly wrong answer. check_harness_fidelity() compares the two vocabularies before every run and prints OK when they agree.

It is not decorative: it is what caught the tubulointerstitial biopsy modifier that had never once fired in the app. If it reports a problem, stop and resolve it before trusting the output. Problems are also written into the summary file so a saved run carries its own warning.

03

Read the output

Per-patient results

<prefix>_results.csv has one row per patient:

ColumnWhat it holds
n_hpoHow many HPO terms the extraction produced. A zero here means the app would have had nothing to score.
hpo_idsThe derived terms, semicolon-separated — use this to audit a surprising result.
p_geneticHeadline probability that any modelled genetic cause explains the presentation. This is the quantity the primary endpoint tests.
top1 · top1_p · top2 · top3The three highest-ranked conditions in the disease-only differential, and the leader's probability. This differential is conditional on there being a monogenic cause, so it stays meaningful even when p_genetic is low.
true_conditionThe confirmed diagnosis, copied from Model_condition.
rank_trueWhere the confirmed diagnosis placed in the differential. Blank for NoGenetic and Not_modelled, which have no rank by construction.
top1_correct · top3_correctWhether the confirmed diagnosis ranked first, or in the top three.
panels_likely · panels_possibleWhich of the 12 panels the app flagged, at each confidence level.
panel_flaggedWhether the panel actually sent was among those flagged. FALSE rows are the interesting ones — read every mismatch individually rather than only the summary rate.
warningsAnything the presentation gate discarded, or a note that no presentation was ticked. Review before analysing.

Study summary

<prefix>_summary.txt holds the pre-specified analysis, printed to the console as well:

FigureHow to read it
Observed diagnostic yieldProportion of tested patients with any P/LP finding, including Not_modelled, with a 95% confidence interval.
Mean predicted p(genetic)What the model expected across the same patients. The comparison of these two lines is the study's primary result.
Brier scoreMean squared error of the headline probability against the binary outcome. Lower is better; it penalises confident wrong answers, which a mean comparison alone can hide.
Top-1 / top-3 accuracyRanking performance among gene-positive patients whose diagnosis the model can express. Not_modelled cases are excluded from the denominator and reported separately, so nothing disappears silently.
Panel sent was flaggedEligibility agreement. A low figure is not automatically a model failure — the discordant cases may be patients who were tested outside criteria.

The summary also states plainly whether the predicted mean fell inside, above, or below the observed confidence interval, so the calibration verdict does not depend on reading two numbers side by side.

To work interactively instead of through the command line, source the pieces directly:

source("data/bayes_params.R"); source("data/panels.R")
source("data/strict_criteria.R"); source("R/bayes.R")
source("R/eligibility.R");        source("R/batch_score.R")

res  <- batch_score_file("RenalGenetics_Validation_Template.xlsx")
summ <- summarise_validation(res)

If you would rather not depend on openxlsx, export the Data Entry sheet to CSV — keeping the column names as the header row — and pass the data frame straight to batch_score().

Handling the data

Never commit the outputs

Both output files contain patient-level clinical data. .gitignore blocks *_results.csv, *_summary.txt and anything matching validation_*, and the completed template is ignored too — but treat that as a safety net, not permission. Keep extraction files and outputs on approved storage only, and use anonymised identifiers in Patient_ID.

On governance: retrospective anonymised extraction by the direct care team for service improvement normally counts as service evaluation rather than research, so no ethics committee approval is needed. That answer changes if the work goes multi-centre or is written up as research. Run the HRA Is my study research? decision tool at the outset and keep the result on file — it takes a few minutes and settles the question before data collection rather than after.
